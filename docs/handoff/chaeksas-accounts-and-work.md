# Chaeksas 작업 요청서 — 계정이 자기 업무(BPM)를 갖고, 다른 계정의 업무를 요청한다

- 보내는 쪽: NowView
- 받는 쪽: Chaeksas (계약·Center·서버 실행기·Studio)
- 작성: 2026-11-01 · 상태: **보내기 전**

이 문서는 Chaeksas 저장소에서 바로 일을 시작할 수 있게 쓴 요청서다. 결정은 Chaeksas가 한다.
`> 제안:`은 NowView의 권고이고, `> 미정:`은 Chaeksas가 정할 것이다. 확인한 Chaeksas 코드·문서는 `main` `aba4219` 기준이다.

## 1. 원하는 모양 (사용자가 정한 것)

```
Center ── 계정 A ── 업무 「아침 메일 처리」      (트리거: 매일 8시)
       │          └ 업무 「구매 요청 처리」      (트리거: 다른 계정의 요청)
       └─ 계정 B ── 업무 「월간 정산」 … 도중에 A의 「구매 요청 처리」를 요청
                                   │
               서비스 태스크 ──▶ 일꾼(C15) ──▶ 회사 시스템
```

1. **Center에는 계정이 있고, 계정에 BPM 프로세스(업무)가 등록돼 있다.** 계정이 실제 사람인지, 「홍길동」인지, 사람이 손대지 않는
   자동 업무만 가진 계정인지 Center는 알 필요가 없다 — **사람/가상 구분을 두지 않는다.**
2. **업무는 트리거로 시작한다** — 시간(타이머), 바깥 사건(이것도 시간 + 서비스 태스크로 「확인」한다), **다른 계정의 요청**.
3. **계정 간 요청** — B의 업무 도중 A에게 할당된 업무를 요청한다. 실제로는 A의 BPM 프로세스가 실행된다.
   * **기다리기**(결과를 받아 B가 잇는다)와 **맡기고 끝**(B는 요청만 남기고 간다) 둘 다 필요하다.
   * **요청할 수 있는 범위는 같은 회사의 계정이다.** 받을지 거부할지는 **A의 BPM 프로세스 안에서** 걸러낸다 — Center·일꾼이
     허용 목록을 두지 않는다.
4. **결재를 누가 받고 누가 답하나는 BPM 프로세스가 회사 규칙으로 정한다.** Center·일꾼은 관여하지 않는다.
5. **Center와 회사 시스템은 서로 의존하지 않는다.** 회사를 만나는 길은 BPM의 서비스 태스크뿐이고, 그것을 일꾼(NowView)이
   가져가 회사 시스템을 부른다(지금 C15 그대로). 회사 시스템이 Center를 깨우는 길은 없다.

## 2. 지금과 어긋나는 것

| 필요 | 지금 Chaeksas | 어긋남 |
|---|---|---|
| 시간 트리거 | 타이머 시작 — Center가 일정을 쥔다(ADR-0110) | 없음 |
| 서비스 태스크 → 바깥 | C15 Pull(ADR-0102) | 없음 |
| 다른 업무를 부르고 결과 받기 | 위임 — 다른 패키지를 자식 실행으로, `parent_run_id`·결과 반환(ADR-0062·0079) | 대상이 **패키지 id**이고 허용 목록이 서명된 `requires.delegations`다 — 「A 계정의 업무」로 부를 수 없다 |
| 맡기고 끝 | 없음 — 위임은 결과를 기다린다(ADR-0079 「기동만 하고 기다리지 않는 위임」 미정) | 새로 필요 |
| **계정** | 관리자 계정(콘솔 로그인, ADR-0090)뿐 | 업무 주체로서의 계정이 없다 |
| **업무가 어느 계정의 것인가** | 배포는 실행기에 붙는다 | 계정 ↔ 업무 묶음이 없다 |
| 회사 | 없음 | 「같은 회사면 요청 가능」을 볼 칸이 없다 |
| 가상 직원 | `virtual_workers` — 접수 Bot 하나 + 감독자 이름(ADR-0085·0098·0099), B16 관문 | 계정이 생기면 **특별한 자원일 이유가 없다** — 자동 업무를 가진 계정이다 |
| 결재 담당자 | `chk:approval.assignees` — 사람 이름 글자(ADR-0080) | 1-4대로 BPM이 정한다면 지금 칸 그대로 쓸 수 있다(아래 R4) |

NowView에서 드러난 증상: 「가상 직원」이 `company1-intake`(접수 Bot 묶음)가 되고 감독자에 사람 이름(이도윤)이 들어가, 콘솔에서
「누가 어떤 업무를 하고 어떤 업무가 할당돼 있나」를 볼 곳이 없었다. 계정마다 업무가 보이면 이 질문이 그 화면 하나로 답해진다.

## 3. 요청

### R1. 계정 자원 — **필수**

> 제안: `accounts` — `id`, `name`(표시 이름, 아무 글이나), `company`(회사 id), `state`(사용·멈춤). 종류·부서·직책 칸은 두지 않는다
> (1-1). 관리자 계정(ADR-0090)과는 별개다 — 콘솔에 로그인하는 사람과 업무 주체는 다르다.
> `state: 멈춤`이면 **그 계정의 트리거가 새 실행을 만들지 않는다**(지금 가상 직원의 `stopped`는 표시뿐이다 — ADR-0085 §1).

> 미정: 계정에 로그인·결재 답 권한을 붙일지(지금은 대리 답용 키 + `X-CHK-On-Behalf-Of`). 1-4대로라면 Center가 정할 일은 아니다.

### R2. 계정에 업무(배포된 BPM 프로세스)를 등록 — **필수**

> 제안: 「계정 X의 업무 = BPM 프로세스 P」 묶음. 그 계정의 업무로 시작한 실행은 `account`를 갖고(C3 `run_started`, CON-01),
> 타이머·요청으로 만든 작업의 `requested_by`도 그 계정이다. 서명된 패키지는 계정을 모른다 — 묶음은 **배포 뒤에** 고친다
> (패키지·배포를 다시 내지 않고 바꿀 수 있어야 한다).

> 미정: 같은 BPM 프로세스를 두 계정이 각자 업무로 가질 수 있나(회사가 여럿이면 필요할 것이다 — 계정·회사마다 실행이 갈린다).

### R3. 계정 간 요청 — **필수**

> 제안: 그림에서 「계정 A의 업무 P를 요청」을 그린다(지금 위임 Call Activity의 대상을 패키지 대신 **계정 + 업무**로).
> `mode: wait | handoff` — `wait`는 지금 위임처럼 결과를 받고, `handoff`는 자식 실행을 만들고 바로 다음으로 간다
> (자식의 끝을 기다리지 않는다, 취소도 따라가지 않는다).
> **허용 검사는 하나다** — 요청한 실행의 계정과 A가 **같은 회사**인가. 아니면 거절(403 `company_mismatch` 같은). 그 밖의 거부는
> A의 BPM이 입력을 보고 걸러 끝낸다(1-3).

> 미정: 지금 위임의 관문(서명된 `requires.delegations`, C2 「서명이 유일한 관문」)과 어떻게 맞출지 — 「같은 회사면 된다」가
> 서명보다 약한 관문인가, 아니면 계정 간 요청은 배포된 업무끼리라 이미 서명된 것들 사이라 괜찮은가.
> 그림에 계정 id를 적을지(배포마다 달라진다), 입력·변수로 받을지.

### R4. 결재 담당은 그림이 정한다 — 바꿀 것 없음(확인만)

1-4대로 결재를 누가 받나는 BPM이 회사 규칙으로 정한다 — 예: 서비스 태스크가 회사 시스템에서 결재자를 읽어 변수로 두고
`assignees`가 그 변수를 쓴다(지금 ADR-0080 그대로). Center는 계정·회사로 담당을 바꾸지 않는다.

> 미정: 「담당자」가 사람 이름 글자 그대로일지, 계정 id일지. NowView는 어느 쪽이든 따른다.

### R5. 가상 직원 자원을 계정으로 접기 — 권함

> 제안: `virtual_workers`(접수 Bot + 감독자)를 「접수 업무를 가진 계정」으로 옮긴다. 감독자 칸 → 접수 BPM이 결재 담당을 스스로
> 정한다(R4). B16 관문(결재 없는 일괄 기동 금지)을 계정 업무 전반에 걸지는 Chaeksas가 정한다 — 1-3·1-4의 「BPM 안에서 거른다」와
> 부딪칠 수 있다.

### R6. 콘솔 — 계정 화면

> 제안: 계정 목록(이름·회사·상태) → 상세: 등록된 업무와 각 업무의 트리거(시간식·요청 받음), 그 계정의 최근 실행, 그 계정이
> 받은·보낸 요청, 열린 결재(그 계정 실행의 것). 「누가 어떤 업무를 하고, 무엇이 그것을 시작시키나」가 이 화면 하나로 보여야 한다.

## 4. NowView가 할 것 (Chaeksas가 정한 뒤)

* 장면 1을 다시 그린다(BPMN 원본은 Company1 리포): 영업 계정의 「고객계획 접수」(타이머 + 「새 원천 확인」 서비스 태스크 →
  회사 수신함)와 「계획 변경 대응」, 대응 도중 생산·자재·경영관리 계정에 업무 요청(지금 SC01 안의 병렬 인수 결재).
* 일꾼 작업을 더한다(수신함 확인·접수 표시 — 회사 시스템 API는 Company1이 낸다). 화면의 「수신」은 「고객이 회사에 보냄」
  (회사 시뮬레이터)만 남기고 Center를 부르지 않는다.
* 엔진의 담당자 표(`domain.ACCOUNTS`·`NODE_ROLES`)와 「담당자 이름 = 역할표」 시험을 새 담당 방식에 맞춘다.
