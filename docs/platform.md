## 1. 세 영역은 세 서버에 나눈다

업무설계서는 「하나의 App 안에서 Dashboard·BPM·Agent 운영을 논리적으로 구분」한다(별도 네 번째 App이나 물리 분리를
전제하지 않는다). 우리는 이미 세 서버로 나눴다(`docs/role-split.md`, 2026-11-03) — 논리 영역을 그 위에 이렇게 놓는다
(2026-11-04 사용자 결정 「역할 분담대로」).

| 영역 (업무설계서 §3·4·6) | 화면 ID | 자리 | 이유 |
|---|---|---|---|
| **Dashboard** — 목표·성과·위험·통제를 잇고 업무로 들어가는 문 | UI-D01 종합 상황판 | NowView `/c/{회사}` (회사 대시보드) | 승인 버튼이 없는 읽기 화면이고 N개 회사를 한곳에서 본다. 숫자는 경영 기록에서 고르기만 한다 |
| **BPM** — 사건별 업무 진행·사람 확인·예외 판단 | UI-B01 업무·Case 목록 · B02 Case와 수행계획 · B03 계획 비교 · B04 업무 확인 · B05 경영검토 · B06 근거·이력 | 회사 사이트 `/work/{회차}/…` | 사람이 하는 일은 회사 사이트다. 결재는 Center 대리 답, 기록은 기간계 |
| **Agent 운영** — 역할·도구·위임·버전·실행 | UI-A01 목록 · A02 위임 구성 · A03 시험·실행 · A04 관리 기준·개선 | NowView `/admin` 쪽(관리자) | Agent·규칙은 NowView(일꾼)의 것이다. 관리 기준 편집은 권한자에게만(설계요약 「화면 구분」) |

* **세 화면은 같은 사건·같은 기준시점을 공유한다**(CP02·05, 8장 「정합성」) — 그 공유는 **경영 기록**이다. NowView가 규칙
  계산 결과를 기간계에 적고(봉투 공통·본문은 종류별 스키마, role-split §3), 대시보드도 회사 사이트도 그 기록만 읽는다.
* **Dashboard → BPM 이동은 서버를 건넌다** — NowView 대시보드의 「사건 열기」가 회사 사이트 Case 화면으로 링크한다(회사
  설정 `site_url` + 경로 + `company_id`·`demo_run_id`·`case_id`·`commitment_id`를 쿼리로 — F01 맥락 유지, X02). 돌아올 때
  대시보드는 같은 세계·필터를 쿼리로 복원한다. 사이트는 NowView를 부르지 않는다는 원칙은 그대로다.
* **화면 이동은 승인·실행·완료를 만들지 않는다**(§2 첫 문단) — 조회 경로에는 쓰기가 없다.

* 기간계 기록 키는 kind/record_id이고 **세계(회차)는 시나리오 하나에 속한다** — 시나리오 2 회차에는 시나리오 2 기록만
  있으므로 접두(`SC0N:`)를 붙이지 않는다. 기록의 `scene`은 그 시나리오의 장면 번호다(「장면 N부터 다시」가 쓴다).
* 공통 칸: 시각은 시간대 있는 ISO(F02, 화면은 KST), `data_as_of`·`calculated_at`(F03), 누락은 `null` + `missing_items`
  (F28 — 0으로 바꾸지 않는다), `execution_mode`(F05 `live_agent`·`rule`·`prepared`·`mock`).
* 스키마는 NowView `docs/records/s2/`에 둔다(시나리오 1 장면 2~7처럼 기본 시연의 모든 판에서 뽑는다).
* **한 기록은 한 장면 문서가 쓴다** — 장면 2는 장면 1의 `case`를 고치지 않고 자기 기록(`case_plan`·`scene` 흐름)에 사건 진행을
  싣는다. 두 문서가 같은 kind/record_id의 판을 따로 세면 기간계에서 엇갈린다. 상황판도 장면마다 다른 id다
  (`company1:ULS:A` · `company1:ULS:A:SC02`).

## 4. 역할·업무 단위 카탈로그 (NowView 코드 — `engine/app/platform/catalog.py`)

* **역할**(CP26) — 사람 H01~H07, Agent A01~A03, 일반 시스템 Y01. 사람·Agent·시스템을 구분해 표시한다 — 정해진
  계산·저장을 모두 Agent로 표현하지 않는다(Y01은 「규칙 엔진」이지 Agent가 아니다). 역할 수 ≠ Agent 수.
* **업무 단위**(CP30) U01~U09 — 이름·연결 단계·필수 여부·수행·책임. 장면 2(N03A)에서 수행계획 항목이 이 id와 버전을
  참조한다.
* **위임 수준**(CP28) A·B·C. 장면 1은 전부 A(조회·분석) — 원천 계획·거래를 바꾸지 않는다.
* **상태 어휘**(업무설계서 §7) — 위험(미평가·주의·위험·허용 범위·관찰), Case(접수·처리 중·확인 대기·경영검토·후속 조치·
  종료), Agent 실행(대기·실행 중·확인 대기·성공·실패·부분 성공·중지). **하나의 완료 표시로 모두 정상 처리하지 않는다.**

## 5. BPM — 정형 흐름과 사건별 수행계획

* **정형 흐름은 BPMN 하나가 한 업무다** — 시나리오 2는 `company1.s2.sc0N`(Company1 `bpm/`, 사이트 `scenarios.py`의 약속).
  서비스 태스크는 기본 확장 `external`의 작업이고 C15 일꾼이 수행한다(시나리오 1과 같다).
* **공통 BPM — 업무 BPM이 호출한다**(2026-11-05 사용자 결정). 업무설계서의 BPM 업무 구간 CP12~17 중 「사건 접수와 영향
  분석」(CP12·15·17)과 Case 연결(CP37)은 시나리오와 무관한 공통 경로라 **공유 BPM 프로세스 `platform.case-intake`**(Company1
  `bpm/platform/`, 패키지 종류 process_lib)로 뽑았다: 경보·원천 Event를 Case에 잇고(`link_case`) → 영향을 분석하고
  (`analyze_case_impact`) → 다음 단계에 인계한다(`hand_off_case_analysis`). **위험 판정은 업무마다 다르므로 부르는 쪽 그림에
  남긴다**(시나리오 2 장면 1은 Y01 입고 변경 경보, 시나리오 1은 고객계획·단가 규칙).
  * **호출은 BPM의 호출 활동(callActivity)이다** — 부르는 패키지가 Studio 「설치」로 공통 BPM을 자기 `libs/`에 받고(판이 적힌
    복사본, BPM ADR-0048), 서버 실행기는 `libs/`를 읽어 **같은 실행 안에서** 돌린다. 그래서 공통 BPM 안의 일감도 실행 신원이
    **바깥 패키지 id**(`company1.s2.sc01`)이고(BPM ADR-0086), 일꾼은 그것으로 업무를 찾아 **그 업무의 규칙으로** 공통 작업을
    수행한다 — 작업 이름은 공통이고 무엇을 Case로 보는지·무엇을 분석하는지는 업무가 정한다(`engine/tests/test_s2_sc01.py`
    `test_common_bpm_jobs_carry_the_calling_package`).
  * **한계 — 복사본이다.** 판이 내보낼 때 고정되므로 공통 BPM을 고치면 판을 올리고 부르는 패키지마다 다시 설치·내보낸다. 진행
    중인 다른 실행을 「참조」할 수는 없다 — 그것은 아래 수행계획(별도 실행 기동·참조)의 몫이다. 사본이 원본과 같은지는 Company1
    `bpm/tests`가 본다.
  * 공통 작업이 다른 업무에서 불리면(시나리오 1 Case 연결 등, §6) 그 업무의 `run_operation`이 같은 이름을 제 규칙으로 구현한다.
* **장면 1은 개정 하나 = 실행 하나다** — 구매 개정이 오면 NowView가 `company1.s2.sc01`을 기동하고(`POST /jobs`, 입력
  `데모실행ID`·`원천개정`), 그림이 Y01 판정 → (경보면) **공통 BPM 호출**(Case 연결 → A01 분석 → 인계)을 돈다. 사람 결재가
  없다 — 장면 1의 사람(생산관리 담당자)은 조회만 한다(「정상 조회를 사람 할 일로 생성하지 않음」).
* **사건별 수행계획(N03A, CP29~38)은 공통 BPM `platform.case-plan`이다**(장면 2, 2026-11-05): A03 제안(`propose_case_plan`) →
  Y01 위임·필수 확인·순서 검사(`check_case_plan`) → 통과하면 적용(`apply_case_plan`), 아니면 차단으로 끝난다. 위임 범위 안 조합은
  사람 승인 없이 적용된다. Case 수행계획 버전(M06)은 NowView 경영 기록 `case_plan`이다.
  * **장면 2의 계획 항목은 그 장면 그림의 단계다**(`link_mode: new` — 같은 실행). 처음 설계 방향은 항목마다 업무 단위 하위
    프로세스를 새 실행으로 기동하는 것이었는데, U01~U05가 한 사건의 순서 그대로라 실행을 나누면 순서를 실행 사이에서 다시 맞춰야
    해서 하지 않았다.
  * **장면 3은 같은 공통 BPM을 다시 부른다**(수행계획 v2 — v1 완료 항목 보존 + U06·조건부 U07). **기존 업무 참조**(`reference`)는
    BPM 실행이 아니라 **회사 시스템의 진행 중 업무**(출하팀 운송 문의 W-TRAN-R)를 가리킨다 — NowView는 읽기만 하고 참조 기록
    (`work_link`)을 남긴다. 그 업무의 새 결과(운송사 회신)는 기간계에 들어오고, 세계 따라가기가 기다리는 실행에 메시지를 보낸다.
  * **사람 결재는 공통 BPM에 두지 않는다**(2026-11-05 확인) — BPM 서버 실행기는 호출 활동 안(자식 실행)의 결재를 Center에 올리지
    않는다(`server_runner/agent.py` `post_approvals`가 최상위 실행만 본다). 그래서 장면 3의 경영검토(U07 — 재보고 → 결정 → 인수)는
    공통 업무 단위인데도 장면 그림에 있다. 실행기가 자식 결재를 올리게 되면 `platform.management-review`로 뽑을 수 있다.
  * BPM 그림은 실행 중에 바뀌지 않으므로 「실행 중 업무 추가」는 그림을 고치는 것이 아니라 계획 새 버전 + 새 실행 기동이다(V01).
  * 계획 적용(`plan_apply`)과 생산계획 확인(`production_plan_apply`, Center 결재 — 생산관리 책임자 한 번)은 다른 승인이다(P03·V04).
* CP40의 「Camunda 구성 확인」은 우리에게는 BPM이다 — 그림 안 호출(호출 활동 + 공유 BPM 패키지)·별도 실행 기동(`POST /jobs`)·
  참조(실행 id 기록)·상태 수신(실행 기록 폴링)은 있다. 실행 중 노드 추가는 없다(위처럼 새 실행으로 푼다).

## 6. 시나리오 1과의 연결 (CP25 — 후속)

시나리오 1의 기록·숫자·승인 순서는 그대로다. 공통 구조로 보완할 것(업무설계서 §9 — 공수는 개발 현황 검토 뒤 확정):
장면 1 고객계획 변경(`EV-S1-VOLUME`)과 장면 2 단가 인상(`EV-S1-PRICE`)을 수익성 대응 Case `CASE-S1-01`의 `event`로 적고
장면 3이 그 Case에서 통합 검토한다. 기존 협상(장면 2 실행)은 `reference`로 잇는다. 이번 판에서는 하지 않았다.

## 7. 업무 번호 — 시나리오 2는 21부터, 시나리오 3은 31부터

NowView 설정(BPM 프로세스 → 업무 번호)·일꾼 라우팅·대시보드가 정수 업무 번호로 장면 처리기를 고른다. 시나리오 1은 1~7
그대로이고 **시나리오 2 장면 N은 20 + N**이다(`company1.s2.sc01` → 21, `company1.s2.sc02` → 22, `company1.s2.sc03` → 23, `company1.s2.sc04` → 24). 문자열 키로 바꾸면 운영 DB에 저장된 설정을
옮겨야 해서 번호 공간을 나눴다 — 번호 → (시나리오, 장면)은 `app/companies.py`의 `WORKS`가 쥔다.
**저장된 설정이 기본값을 이기므로** 운영·로컬 엔진에는 관리자 모드로 `company1.s2.sc01 → 21`·`company1.s2.sc02 → 22`·
`company1.s2.sc03 → 23`·`company1.s2.sc04 → 24`를 더해야
일꾼이 그 일감을 받는다. 사이트 명령(「장면 열기」 등)의 장면은 그 회차 시나리오의 장면 번호다(업무 번호가 아니다).

**시나리오 3 장면 N은 30 + N**이다(`company1.s3.sc01` → 31, `company1.s3.sc02` → 32, `docs/s3/common.md`). 같은 이유로 저장된
설정에는 관리자 모드로 `company1.s3.sc01 → 31`·`company1.s3.sc02 → 32`를 더한다.
