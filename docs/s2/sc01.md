## 흐름

```
사이트(시연) ─구매 개정 등록─▶ 기간계 수신함 ─▶ NowView 세계 따라가기 ─POST /jobs─▶ Center(company1.s2.sc01)
                                                                                   │ 개정 하나 = 실행 하나
         Task_Evaluate(Y01) ─경보?─▶ Call_CaseIntake ─────────────────────────────────────▶ End (N03A 대기)
                         │              └ 공통 BPM platform.case-intake (같은 실행 안):
                         │                Task_Link(Y01 link_case) ─▶ Task_Analyze(A01 analyze_case_impact)
                         │                ─▶ Task_Handoff(hand_off_case_analysis)
                         └─ 아니면 ─▶ End_Recorded(이력만)
   서비스 태스크는 C15 일꾼(`app/s2/sc01/process.py` run_operation) → 경영 기록을 기간계에 적는다
```

* **사람 결재가 없다** — 생산관리 담당자는 상황판(NowView)·사건 화면(사이트)을 조회만 한다. 실행이 끝났는지는 일감이 알려
  준다(판정이 경보가 아니면 「이력만」 끝, 인계 다음이 끝). 일감이 오기 전에 실행이 실패하면 알려 줄 일감이 없으므로 폴러가
  도는 개정의 Center 작업 상태를 읽어 실패와 사유를 남긴다(`bpm.state`가 `running`인 문서만).
* **판정만 이 업무의 그림이고 경보 뒤는 공통 BPM 호출이다**(`docs/platform.md` §5, 2026-11-05). 공통 BPM 안의 일감도 실행
  신원이 `company1.s2.sc01`이라 일꾼이 이 업무로 보내고, 공통 작업 셋을 이 업무의 규칙(공급 대응 Case·A01 납기 영향)으로 한다.
* **업무 번호 21**(`docs/platform.md` §7). 설정 매핑 `company1.s2.sc01 → 21`, 패키지 `CHAEKSAS_S2_SC01_PACKAGE`.
* Center 멱등 키 `s2sc01:{회차}:e{center_epoch}:{수신 문서}` — 초기화 뒤 옛 작업이 돌아오지 않게 문서마다 다른 값을 넣는다.

## 규칙 (구현명세 §3 Y01 · `app/s2/sc01/calc.py`)

* 같은 개정의 재수신은 판정 `DUPLICATE`(평가하지 않는다 — 경보·Case·분석 각 1, T05). 앞선 개정이 늦게 오면 `LATE`
  (이력 보존·최신값 유지).
* 최근 **3 공장 영업일**(판정일 포함, 월~금) 안의 실제 변경 수. 최초 등록은 빼고 센다.
* 첫 변경: 필요 시각 부족 > 0 **또는** 최소 착수 여유 < 15분(초 단위로 판정 — 정확히 15분은 기록만)이면 경보. 판정에 필요한
  자료가 없고 다른 조건으로 경보를 확정할 수 없으면 `HOLD`(평가 보류 — 정상이 아니다). 두 번째 변경부터는 규모와 관계없이 경보.
* **배정은 계산이다** — 같은 부품의 입고분을 기존 조립 착수가 이른 약정부터 채운다. P-v2에서 COM-S ← L2S, COM-R ← L2R이
  나온다(주문영향 시트의 「배정 입고분」과 같다). 사용 가능 = 입고예정 + 검수 30분.
* A01은 **규칙 처리**다(`execution_mode: rule`) — 가상자료 재현을 실제 AI 호출로 표시하지 않는다. 차량 마감이 없으면 그 칸은
  `null`·「출하 영향 미확인」이고 운송 가능 여부를 추정하지 않는다(T07).
* A01 실패(사례 `A01-FAIL`)는 503 → 일꾼 `dependency_down`(Center가 다시 내준다). 실패 시도는 남기고 완료로 보이지 않는다(T08).

## 경영 기록 (공통 종류 — `docs/records/s2/sc01/`)

`scene`(S2:SC01) · `event`(EV-S2-01-R0~R2) · `alert`(AL-S2-01) · `case`(CASE-S2-01 — 역할 목록·흐름 단계 포함) ·
`analysis`(ANA-01 — 판) · `handoff`(HAND-01) · `dashboard`(company1:ULS:A — UI-D01). 스키마는 기본 시연의 모든 판에서
뽑았다(`records_contract.check(…, "s2/sc01")`).

## 화면

| 화면 | 자리 | 무엇 |
|---|---|---|
| UI-D01 납기 상황판 (D01) | NowView `/c/company1?world=…` (시나리오 2 회차) | 성과(OTD 99% / 98%)·위험(경보 1 / 약정 2)·통제(영향 분석 완료 / 생산계획 변경 전), 관심 사건 + 「사건 열기」, 변경 전후, 모델별 실적, 도래 전 약정 |
| UI-B02 Case (D02) | 회사 사이트 `/work/{회차}/s2/sc01?back=…` | 참여 역할(사람·Agent·시스템) · 흐름 N01~N03A · 근거(원천 개정·자료시각·실행 방식) · S/R 표 · 개정 이력 · 인계. 승인·완료 버튼 없음 |

「사건 열기」는 돌아올 주소(`back`)와 회차를 넘긴다 — 사이트는 NowView를 부르지 않고 링크만 건다.

## 남은 것

* **Center에 올릴 것(사람이 한다)**: 확장 `external` 0.9.0은 일꾼이 뜰 때 올린다. Studio에서 ① `platform.case-intake` 0.1.0을
  **공유 BPM 패키지**로 내보내 승인(2026-11-05 올렸다), ② Studio 작업 폴더의 `company1.s2.sc01`을 열고 공유 BPM 프로세스
  `platform.case-intake` 0.1.0을 **「설치」**(그 패키지의 `libs/`에 사본과 설치 기록이 생긴다) → 0.9.1로 내보내 승인·배포.
  **설치는 Studio 작업 폴더에서 해야 한다** — 리포의 `libs/`·기록은 원본 쪽 사본이고, Studio는 제 작업 폴더
  (`~/.local/share/BPM/studio/workspace/기본/`)를 내보낸다.
* **2026-11-05 로컬 Center 실측 — 설치 없이 내보낸 0.9.0**: 패키지에 `libs/`가 없고 `requires.libs`에 판 없는 id만 적힌 채
  Studio 내보내기·Center 승인·배포를 모두 지났다. P-v0·P-v1은 판정만 돌아 「이력만」으로 끝났고(일감 2건 `complete`), P-v2는
  경보 판정 뒤 호출 활동에서 `call_target_missing`(있는 것: `company1.s2.sc01`)으로 실행이 실패했다 — 일감이 없어 NowView는
  그 개정을 계속 「실행 중」으로 뒀다. 그래서 **폴러가 시나리오 2의 도는 개정도 읽는다**(`poll_center` — 작업 상태로 거절·취소·
  실패를 사유와 함께 남긴다). 호출 대상이 빠진 패키지를 내보내기·승인 때 막지 않은 것은 BPM 쪽 빈틈이다.
* **2026-11-05 로컬 Center 실측 — 0.9.1(공통 BPM 설치 후)**: 서버 실행기 설치본에 `libs/platform.case-intake__case-intake.bpmn`이
  있다. 회차 `demo-10fdeecb`에서 P-v0·P-v1은 「이력만」, P-v2는 **실행 하나 안에서** 호출 활동 `Call_CaseIntake`가 공통 BPM을
  띄워 `link_case` → `analyze_case_impact` → `hand_off_case_analysis`를 돌고 `success`로 끝났다(개정마다 4~10초). 공통 BPM 안의
  일감도 업무 21로 갔고 일꾼 일감 6건 실패 0. CASE-S2-01 ANALYZED · 약정 S·R · 착수 차질 90분·150분 · N03A 인계 · 승인 0건이

  설정되지 않았다」·`no_deployment` 사유로 남는다.
